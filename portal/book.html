Capítulo 1

Introdução e status

W é uma proposta de linguagem de sistemas nativa. Seu norte combina prazer de uso com previsibilidade: falha, suspensão, mutação, transferência e paralelismo devem aparecer no contrato ou no ponto em que acontecem.

Direção

Os princípios são a base de trabalho. Sintaxe, semântica e arquitetura continuam em diferentes graus de maturidade.

Leia cada exemplo com o rótulo correto. Direção é uma intenção estável; Candidato é uma baseline coerente ainda não provada; Em aberto conserva alternativas legítimas. Hoje não existe compilador, runtime ou stdlib W implementado.

Continue nas fontes: visão do projeto · registro de status.

Capítulo 2

Primeiro programa

Um programa começa com imports lógicos e uma função main. O manifest e o lockfile resolvem de onde vem std; o source não espalha URLs e hashes.

import { io } from std

fn main() {
  io.print("Olá, W!")
}

Arquivos são UTF-8. Quebras de linha encerram a maior parte das declarações. Essas formas são exemplos dourados de design: você pode estudá-las e editá-las no playground, mas ainda não executá-las.

Experimente: abra este exemplo no Playground e observe os tokens reconhecidos.

Capítulo 3

Bindings e funções

const nomeia um valor disponível no compile time hermético; let cria um binding runtime que não pode ser reatribuído; var torna a reatribuição explícita.

const maxConnections = 512
let host = "127.0.0.1"
var served = 0

fn welcome(to guest: String): String {
  return "Olá, ${guest}!"
}

Funções usam uma forma canônica: fn nome(label: Tipo): Retorno. Labels fazem a chamada ler como uma frase; _ pode retirar o label quando isso torna a API mais clara. Efeitos candidatos ficam no contrato, como em async throws LoadError.

Detalhes: sintaxe de trabalho.

Capítulo 4

Tipos, options e errors

As categorias contam uma história de custo e comportamento: struct é valor, object tem identidade, enum fecha alternativas e protocol descreve capacidade sem storage escondido.

struct User {
  id: UserId
  name: String
}

enum LoadError: Error {
  notFound(UserId)
  transport(HttpError)
}

fn find(id: UserId): User?
fn load(id: UserId): User throws LoadError

T? tem somente .some(T) e .none; não mistura ausência com vazio, não inicializado ou ponteiro nulo. Erros recuperáveis são tipados por throws E, propagados por try e tratados por cases. Na baseline, error sets diferentes exigem conversão explícita com catch; isso não promete exceptions ocultas.

Modelos: tipos e memória · options e errors.

Capítulo 5

Controle e strings

if, guard, loops e switch favorecem fluxo local e cases exaustivos. Não há fallthrough implícito no switch candidato.

guard let user = find(id) else return .notFound

switch user.role {
  case .admin: showAdmin(user)
  case .member: showProfile(user)
}

String contém UTF-8 válido, mas “comprimento” não é uma unidade única. Bytes, escalares Unicode e grafemas são views distintas; APIs devem nomear byteCount, scalarCount ou graphemeCount e deixar o custo visível.

Capítulo 6

Ownership e memória

O caminho comum busca owner único e borrows locais inferidos. A sintaxe aparece quando a história muda: ref empresta para leitura, inout dá acesso mutável exclusivo, take transfere ownership e copy pede uma cópia.

fn inspect(value: ref Value)
mut fn edit(value: inout Value)
fn store(value: take Value)

inspect(value)
edit(inout value)
store(take value) // value não está mais disponível

Shared ownership, ARC e regions ainda exigem protótipos. A direção é segurança sem dangling pointers ou data races; a estratégia exata de memória compartilhada permanece Em aberto.

Contrato candidato: ownership, regiões e FFI.

Capítulo 7

Concorrência e paralelismo

async let inicia um filho concorrente: trabalhos podem progredir intercalados sem prometer outro núcleo. spawn let solicita um filho paralelo e, por isso, exige transferência segura de dados.

async let user = loadUser(id)
async let feed = loadFeed(id)
let page = try await (user, feed)

spawn let digest = hash(take bytes)
let value = await digest

Ambos vivem numa árvore estruturada: o scope possui os filhos, propaga cancelamento e não termina antes de join e cleanup. O executor pode usar event loop, pool ou outra política; nenhuma dessas estratégias está implementada hoje.

Semântica: tasks, cancelamento e executores.

Capítulo 8

Módulos, services e workers

Um módulo organiza namespace e build; ele não ganha heap, thread ou lifecycle singleton por existir. Importar resolve símbolos, não consulta a rede, concede capabilities ou inicia uma instância. Estado duradouro pertence a objetos ou instâncias runtime explícitas.

Candidato

A separação entre módulo estático, instância de service e worker precisa ser validada. ServiceHost, service, worker e isolate ainda não são API ou keywords congeladas.

protocol CatalogApi {
  fn list(): Array<Item> async throws CatalogError
}

enum CatalogAppError: Error {
  start(StartError)
  catalog(CatalogError)
}

fn startCatalog(host: inout ServiceHost): ServiceRef<CatalogApi> async throws CatalogAppError {
  do {
    return try await host.startService(
      CatalogState(), as: CatalogApi, scope: .process, policy: .serial,
    )
  } catch let error {
    throw .start(error)
  }
}

fn loadItems(catalog: ServiceRef<CatalogApi>): Array<Item> async throws CatalogAppError {
  do {
    return try await catalog.list()
  } catch let error {
    throw .catalog(error)
  }
}

fn main(host: inout ServiceHost): Void async throws CatalogAppError {
  let catalog = try await startCatalog(inout host)
  let items = try await loadItems(catalog)
}

Leia os contratos dedicados: spec/modules.md · design/modules-and-runtime.md. O primeiro é semântico; o segundo descreve arquitetura candidata, não implementação disponível.

Capítulo 9 · exemplo top-down

O restaurante W

Um pedido de bolo conecta as ideias anteriores sem esconder fronteiras. O menu escolhe um fluxo com switch; uma instância candidata keyed por pedido mantém estado serial; a cozinha usa children concorrentes durante espera e trabalho paralelo para lotes independentes.

Uma mesa completa revela outro detalhe: o mesmo ServiceHost entra como inout, portanto os pedidos keyed são abertos sequencialmente. Só depois, com três handles independentes, os pratos progridem juntos:

let cakeOrder = try await openMenuOrder(request.cake.orderId, on: inout orders)
let soupOrder = try await openMenuOrder(request.soup.orderId, on: inout orders)
let saladOrder = try await openMenuOrder(request.salad.orderId, on: inout orders)

async let cake = prepareMenuCake(request.cake, for: cakeOrder, in: kitchen)
async let soup = prepareMenuSoup(request.soup, for: soupOrder, in: kitchen)
async let salad = prepareMenuSalad(request.salad, for: saladOrder, in: kitchen)
let (cake, soup, salad) = try await (cake, soup, salad)

Fine-grained não significa RPC por função. A fronteira existe quando estado, lifetime, isolamento ou escala justificam; toda call entre instâncias continua suspensível, falível e cancelável.

Pressão volta ao caller. Mailbox limitada aguarda vaga ou produz overload tipado; nunca descarta pedido silenciosamente.

Children pertencem ao handler. Error ou cancelamento encerra a árvore, faz join e executa defer/cleanup antes de sair.

Estado externo exige compensação. Cancelar as child tasks não desfaz silenciosamente uma instância OrderState; cancelBirthdayTable torna essa ação explícita.

Explore o exemplo: leia a narrativa completa · edite a cozinha · abra a mesa completa.

Contratos: concorrência estruturada · instâncias e calls tipadas · arquitetura candidata.

Capítulo 10

FFI

C é uma ABI de primeira classe e uma fronteira nomeada. Declarações foreign c expõem raw pointers e layouts; wrappers seguros restauram ownership, optional, slices e typed errors.

foreign c from "sqlite3.h" {
  type sqlite3
  fn sqlite3_close(handle: c.ptr<sqlite3>): c.int
}

Um ponteiro non-null não é prova de validade. Allocator e deallocator precisam combinar; callbacks precisam declarar ownership do contexto e regras de thread. O bloco foreign pode quebrar garantias, mas sua API pública deve restabelecê-las.

Capítulo 11

Packages e reprodutibilidade

O manifest declara dependências lógicas; um lockfile resolvido fixa grafo, origem e integridade. Cache por conteúdo, provenance e SBOM tornam o build auditável. Uma hash isolada prova integridade, não autoria ou segurança.

Direção

Toolchain e supply chain são parte do produto W desde cedo. O sistema descrito ainda é design, não um gerenciador disponível.

Build reproduzível é uma propriedade testável: mesmas entradas e ambiente normalizado devem produzir o mesmo artefato. Binários podem ser preferidos quando compatíveis, mas fonte continua sendo um artefato verificável.

Arquitetura: packages, builds e confiança.
