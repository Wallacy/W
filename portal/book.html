Capítulo 1

Introdução e status

W é uma proposta de linguagem de sistemas nativa. Seu norte combina prazer de uso com previsibilidade: falha, suspensão, mutação, transferência e paralelismo devem aparecer no contrato ou no ponto em que acontecem.

Direção

Os princípios são a base de trabalho. Sintaxe, semântica e arquitetura continuam em diferentes graus de maturidade.

Leia cada exemplo com o rótulo correto. Direção é uma intenção estável; Candidato é uma baseline coerente ainda não provada; Em aberto conserva alternativas legítimas. Hoje não existe compilador, runtime ou stdlib W implementado.

Continue nas fontes: visão do projeto · registro de status · revisão integral da DB1.

Capítulo 2

Primeiro programa

Um programa começa com uma função main. A proposta DB1 usa uma prelude T0 pequena e congelada pela edição; dependências da aplicação continuam usando imports lógicos. Manifest e lockfile resolvem ambos sem espalhar URLs e hashes pelo source.

fn main() {
  print("Olá, W!")
}

Arquivos são UTF-8. Quebras de linha encerram a maior parte das declarações. Essas formas são exemplos dourados de design: você pode estudá-las e editá-las no playground, mas ainda não executá-las.

Experimente: abra este exemplo no Playground e observe os tokens reconhecidos.

Capítulo 3

Bindings e funções

const nomeia um valor disponível no compile time hermético; let cria um binding runtime que não pode ser reatribuído; var torna a reatribuição explícita.

const maxConnections = 512
let host = "127.0.0.1"
var served = 0

fn welcome(to guest: String): String {
  return "Olá, ${guest}!"
}

Funções usam uma forma canônica: fn nome(label: Tipo): Retorno. Labels fazem a chamada ler como uma frase; _ pode retirar o label quando isso torna a API mais clara. Efeitos candidatos ficam no contrato, como em async throws LoadError.

Detalhes: sintaxe de trabalho.

Capítulo 4

Tipos, options e errors

As categorias contam uma história de custo e comportamento: struct é valor, object tem identidade, enum fecha alternativas e protocol descreve capacidade sem storage escondido.

struct User {
  id: UserId
  name: String
}

enum LoadError: Error {
  notFound(UserId)
  transport(HttpError)
}

fn find(id: UserId): User?
fn load(id: UserId): User throws LoadError

T? tem somente .some(T) e .none; não mistura ausência com vazio, não inicializado ou ponteiro nulo. Erros recuperáveis são tipados por throws E, propagados por try e tratados por cases. Na baseline, error sets diferentes exigem conversão explícita com catch; isso não promete exceptions ocultas.

Property behaviors: storage sem boilerplate

W-O097 pesquisa uma abstração tipada para uma propriedade controlar storage, inicialização e accessors sem mudar seu tipo lógico. Ela pode cobrir lazy, init tardio, observers, COW e policies locais, mas não pode disfarçar suspensão, rede ou falha como leitura de field.

// Hipótese visual; ainda não pertence à grammar.
object Oven {
  var Lazy heatProfile = deriveHeatProfile(model)
}
Property behaviors · Pesquisa

A recomendação conjunta é var Lazy heatProfile = expression: var ancora a declaração e o behavior fica imediatamente antes do nome. Lazy var heatProfile permanece a alternativa humana mais próxima, mas mistura behaviors com a ordem de export, ownership e outros modifiers. by, with, prefixo no initializer, var [behavior], wrapper nominal e bloco na propriedade continuam preservados. Init/set, modify, efeitos, composição, acesso a self, layout e Sendable precisam fechar juntos; isso não reabre annotations genéricas.

Modelos: tipos e memória · options e errors.

Pesquisa: property behaviors e alternativas.

Capítulo 5

Controle e strings

if, guard, loops e switch favorecem fluxo local e cases exaustivos. Não há fallthrough implícito no switch candidato.

guard let user = find(id) else return .notFound

switch user.role {
  case .admin: showAdmin(user)
  case .member: showProfile(user)
}

String contém UTF-8 válido, mas “comprimento” não é uma unidade única. Bytes, escalares Unicode e grafemas são views distintas; APIs devem nomear byteCount, scalarCount ou graphemeCount e deixar o custo visível.

Capítulo 6

Ownership e memória

O caminho comum busca owner único e borrows locais inferidos. A sintaxe aparece quando a história muda: ref empresta para leitura, inout dá acesso mutável exclusivo, take transfere ownership e copy pede uma cópia.

fn inspect(value: ref Value)
mut fn edit(value: inout Value)
fn store(value: take Value)

inspect(value)
edit(inout value)
store(take value) // value não está mais disponível

Shared ownership, ARC e regions ainda exigem protótipos. A direção é segurança sem dangling pointers ou data races; a estratégia exata de memória compartilhada permanece Em aberto.

Layout e ABI · Proposta DB1

Structs W comuns têm layout opaco entre builds, mas consultável por sizeOf, alignOf e w explain layout. Tipos em foreign c adotam a ABI C do target; type UserId = u64 cria um newtype nominal sem storage adicional e alias cria apenas um sinônimo. A v0 pública inclui packed/aligned seguros para hardware e formatos exatos, sem congelar uma ABI W universal. Ordem física default, transparent struct e fixed struct permanecem alternativas.

Contrato candidato: ownership, regiões e FFI.

Capítulo 7

Concorrência e paralelismo

async let inicia um filho concorrente: trabalhos podem progredir intercalados sem prometer outro núcleo. spawn let solicita um filho paralelo e, por isso, exige transferência segura de dados.

async let user = loadUser(id)
async let feed = loadFeed(id)
let page = try await (user, feed)

spawn let digest = hash(take bytes)
let value = await digest

Ambos vivem numa árvore estruturada: o scope possui os filhos, propaga cancelamento e não termina antes de join e cleanup. O executor pode usar event loop, pool ou outra política; nenhuma dessas estratégias está implementada hoje.

Semântica: tasks, cancelamento e executores.

Capítulo 8

Módulos, services e workers

Um módulo organiza namespace e build; ele não ganha heap, thread ou lifecycle singleton por existir. Importar resolve símbolos, não consulta a rede, concede capabilities ou inicia uma instância. Estado duradouro pertence a objetos ou instâncias runtime explícitas.

Candidato

A separação entre módulo estático, instância de service e worker precisa ser validada. ServiceHost, service, worker e isolate ainda não são API ou keywords congeladas.

protocol CatalogApi {
  fn list(): Array<Item> async throws CatalogError
}

enum CatalogAppError: Error {
  start(StartError)
  catalog(CatalogError)
}

fn startCatalog(host: inout ServiceHost): ServiceRef<CatalogApi> async throws CatalogAppError {
  do {
    return try await host.startService(
      CatalogState(), as: CatalogApi, scope: .process, policy: .serial,
    )
  } catch let error {
    throw .start(error)
  }
}

fn loadItems(catalog: ServiceRef<CatalogApi>): Array<Item> async throws CatalogAppError {
  do {
    return try await catalog.list()
  } catch let error {
    throw .catalog(error)
  }
}

fn main(host: inout ServiceHost): Void async throws CatalogAppError {
  let catalog = try await startCatalog(inout host)
  let items = try await loadItems(catalog)
}

Leia os contratos dedicados: spec/modules.md · design/modules-and-runtime.md. O primeiro é semântico; o segundo descreve arquitetura candidata, não implementação disponível.

Capítulo 9 · exemplo top-down

O restaurante W

Um pedido de bolo conecta as ideias anteriores sem esconder fronteiras. O menu escolhe um fluxo com switch; uma instância candidata keyed por pedido mantém estado serial; a cozinha usa children concorrentes durante espera e trabalho paralelo para lotes independentes. Equipamento, scheduling, billing, TUI e HTTP acrescentam cálculo e lifecycle reais ao mesmo corpus.

Uma mesa completa revela outro detalhe: o mesmo ServiceHost entra como inout, portanto os pedidos keyed são abertos sequencialmente. Só depois, com três handles independentes, os pratos progridem juntos:

let cakeOrder = try await openMenuOrder(request.cake.orderId, on: inout orders)
let soupOrder = try await openMenuOrder(request.soup.orderId, on: inout orders)
let saladOrder = try await openMenuOrder(request.salad.orderId, on: inout orders)

async let cake = prepareMenuCake(request.cake, for: cakeOrder, in: kitchen)
async let soup = prepareMenuSoup(request.soup, for: soupOrder, in: kitchen)
async let salad = prepareMenuSalad(request.salad, for: saladOrder, in: kitchen)
let (cake, soup, salad) = try await (cake, soup, salad)

Fine-grained não significa RPC por função. A fronteira existe quando estado, lifetime, isolamento ou escala justificam; toda call entre instâncias continua suspensível, falível e cancelável.

Pressão volta ao caller. Mailbox limitada aguarda vaga ou produz overload tipado; nunca descarta pedido silenciosamente.

Children pertencem ao handler. Error ou cancelamento encerra a árvore, faz join e executa defer/cleanup antes de sair.

Estado externo exige compensação. Cancelar as child tasks não desfaz silenciosamente uma instância OrderState; cancelBirthdayTable torna essa ação explícita.

O restaurante também calcula

O modelo térmico separa funções puras da boundary de hardware. Quantidades incompatíveis devem falhar no type checker; o loop assíncrono fica apenas onde sensor, actuator e timer realmente suspendem.

let wallLoss = surface * transmittance * (inside - ambient)
let cavityEnergy = (heaterPower * duty - wallLoss - foodTransfer) * elapsed
let nextCavity = cavity + cavityEnergy / cavityCapacity

planning.w executa earliest-deadline-first e escolhe a lane menos carregada. billing.w calcula imposto em minor units com rounding explícito. Nenhuma dessas funções precisa de task, service ou framework.

Mesma regra, intenções diferentes

A integração do PID usa switch rawDuty com ranges one-sided e guards where. A expressão direta com in/||/&& e uma futura tuple-pattern permanecem documentadas como alternativas; where refina patterns, não duplica todo operador booleano.

switch rawDuty {
  case 0.0...1.0: return true
  case ..<0.0 where error > 0.0: return true
  case 1.0>.. where error < 0.0: return true
  case _: return false
}

A forma booleana é a alternativa mais direta quando a política não merece nome ou pattern matching:

let canAccumulate = rawDuty in 0.0...1.0
  || (rawDuty < 0.0 && error > 0.0)
  || (rawDuty > 1.0 && error < 0.0)

Uma futura tuple-pattern poderia agrupar os três casos num único case; ela só será candidata se o match múltiplo ficar mais legível que os guards e produzir diagnostics melhores.

TUI e HTTP compartilham uma facade

async let terminal = runTerminalInterface(restaurant)
async let web = runWebInterface(address, restaurant)
let (_, _) = try await (terminal, web)

print, readLine, http e json testam a superfície std implícita da edição. Os imports entre módulos do restaurante continuam explícitos. Nome visível não concede terminal, socket ou rede: effects, capabilities e reachability continuam observáveis.

Laboratório de alternativas

Membership · Proposta DB1

next in (.preparing, .cancelled) é um teste finito intrínseco e sem allocation. Alternativas preservadas: next.isOneOf(...), a forma explícita com == || e patterns. Flags usam operações distintas, como hasAny/hasAll.

Std implícita · Proposta DB1

Prelude T0 pequena e congelada por edição, incluindo print; namespaces oficiais continuam disponíveis. Alternativas: todo export único ou somente namespaces com pouquíssimos nomes livres. Todas preservam origem, reachability e capability no tooling.

Visibilidade · Candidato

Privado por default e export para a interface. Alternativas para values com invariantes: fields exportados, tipo opaco ou factories. public/private seguem desnecessários no corpus.

Labels · Candidato

Primeiro argumento posicional, seguintes nomeados. Alternativas: todos nomeados ou todos posicionais com lint. Labels customizados continuam parte da API.

Unidades · Proposta DB1

180[°C] usa uma unit expression delimitada. std.si T2 cobre o SI oficial completo, dimensões, prefixos e temperatura ponto/delta; suffix, Number<Unit> e wrappers continuam alternativas. Unidades apagam no lowering quando não são observadas.

Exponenciação · Proposta DB1

flow ** 2 é o operador, associativo à direita e mais forte que unary minus; pow continua API para famílias e casos especiais. Multiplicação explícita permanece sempre válida.

Ranges · Proposta DB1

..., ..<, >.. e >..< descrevem bounds; stride descreve progressão. Range fechado oferece clamp; intersection retorna range opcional e union possivelmente descontígua produz RangeSet. Clamped não precisa ser uma feature do core.

HTTP · Proposta DB1

TCP/UDP/DNS ficam no T1; HTTP/TLS são módulos T2 oficiais, bundled e versionados pelo package/lock para receber correções fora da edição da linguagem. Manter apenas transporte oficial ou usar pacote comunitário continuam alternativas.

Serviço · Proposta DB1

service é açúcar próprio sobre object + descriptor, com ServiceRef sempre async. Object/protocol explícitos e metadata sem keyword permanecem alternativas; placement local/remoto nunca é escondido pelo import.

Capítulo 10

FFI

C é uma ABI de primeira classe e uma fronteira nomeada. Declarações foreign c expõem raw pointers e layouts; wrappers seguros restauram ownership, optional, slices e typed errors.

foreign c from "sqlite3.h" {
  type sqlite3
  fn sqlite3_close(handle: c.ptr<sqlite3>): c.int
}

Um ponteiro non-null não é prova de validade. Allocator e deallocator precisam combinar; callbacks precisam declarar ownership do contexto e regras de thread. O bloco foreign pode quebrar garantias, mas sua API pública deve restabelecê-las.

Uma call W, várias implementações possíveis

O equipamento do restaurante testa a ideia histórica de funções multilíngues para migração. O body C pertence à própria aplicação — não é uma library externa — enquanto o call site continua W comum e tipado.

let temperature = try equipment.read(.cavity)

// Baseline implementável: ABI declarada e wrapper W seguro.
foreign c from "restaurant_equipment.h" { /* declarations */ }

// Pesquisa: ilha compilada pelo frontend C junto da aplicação.
fn<C> readProbeRaw(_ handle: c.ptr<restaurant_equipment>, _ probe: c.int): c.double {
  double value = 0.0;
  return restaurant_read_probe(handle, probe, &value) == 0 ? value : NAN;
}
fn<lang> · Pesquisa

Body inline é a hipótese principal. fn<C> ... from mantém o source da aplicação em arquivo separado; fn<C::equipment> agrupa uma compilation unit; um adapter declarado evita gramática especial. LLVM/MLIR comum ajuda no lowering, mas não substitui contratos de ABI, runtime, ownership, exceptions e source maps. Nenhuma forma pertence à grammar atual.

Experimento completo: funções multilíngues · wrapper C do equipamento · comparação visual.

Capítulo 11

Packages e reprodutibilidade

O manifest declara dependências lógicas; um lockfile resolvido fixa grafo, origem e integridade. Cache por conteúdo, provenance e SBOM tornam o build auditável. Uma hash isolada prova integridade, não autoria ou segurança.

Direção

Toolchain e supply chain são parte do produto W desde cedo. O sistema descrito ainda é design, não um gerenciador disponível.

Build reproduzível é uma propriedade testável: mesmas entradas e ambiente normalizado devem produzir o mesmo artefato. Binários podem ser preferidos quando compatíveis, mas fonte continua sendo um artefato verificável.
